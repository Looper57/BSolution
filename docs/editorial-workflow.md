# Private employer-content queue

This is a local editorial preflight and handoff tool. It does not publish pages, schedule an external service, create AI content, authenticate reviewers or replace the existing owner/evidence and deployment gates. Its generic code and synthetic tests can live in the repository. Actual topics, drafts, reviewer records, demand data and reports belong outside the public repository in the shared workspace.

Run `pnpm content:queue --input /absolute/path/to/private-queue.json` to inspect tasks and dates. An optional `--as-of YYYY-MM-DD` makes a historical evaluation reproducible. `--prepare task-id` exits unsuccessfully unless the whole queue is valid and that exact task is approved, current and reviewed. A successful preparation returns only the revision and task summary, never the draft body. This output is a handoff to normal source review and release, not an authorization to bypass either. No file is modified by the command.

A version1 queue contains tasks with stable IDs, audience (`law-firm` or `in-house`), locale, situation, existing canonical `targetPath`, rationale, next action, next-review date and state: proposed, research, draft, review, approved, published or paused. The approved employer inventory determines valid targets without requesting job feeds. This first version intentionally updates existing routes; new pages require their own ordinary route/evidence review. Two active tasks cannot compete for the same target. Scheduling reports due dates; it does not run a background scheduler. Pausing a task prevents preparation; it does not unpublish an already deployed page.

Draft content contains a title, body, sources and claims. Sources record credential-free HTTPS URLs, dates actually checked and the statement they support. Every declared factual claim names its sources. Company-experience claims additionally require the existing approved evidence ID, exact approved page ID and language. A competitor's capabilities cannot authorize a B Solution experience claim. The tool validates the recorded mapping, not the truth of an external page or completeness of declared claims. Editorial review must actually check the text, including undeclared factual assertions and confidential data.

An editorial review records the real reviewer, actual date, revision and affirmative checks for facts, confidentiality, invented experience, employer usefulness, language and links. Calculate the revision from the validated task with `contentRevision`; the inspection report includes it. Any change to text, sources, claim mapping, audience, route, language, situation or next action invalidates that review. State and review scheduling can change without rewriting text. An expired review, impossible/future date or unchecked source added after review blocks preparation. These are recorded editorial assertions, not a digital signature or a new owner approval.

A published record needs the same content revision, deployment-source commit, verified canonical URL, actual date and rollback commit. These references are validated structurally; actual CI, deployment, HTTP and visible-page verification must still be performed and retained before recording publication. No genuine reviewed date, author, permission, deployment or rank gain is inferred from the record's presence. Existing manually implemented pages are not retroactively labelled as published through this workflow.

Keep private queues outside Git. The CLI omits source/draft/reviewer contents and parser input excerpts from reports and errors. A report is still an internal editorial artifact. The existing site imports none of these scripts or private files, so queue state cannot create public routes, sitemap entries or structured data. Current source/deployment/graph/browser gates remain mandatory. Changes made directly to public source code remain governed by those existing checks; this preflight alone is not a repository-wide automatic publication firewall.

## Stage approved text for the website

`pnpm content:stage --input /absolute/private-queue.json --task task-id --registry lib/editorial/published.json --output /absolute/new-candidate.json` creates a new public candidate file. The output must not already exist; files and symlinks are never overwritten. Input and the existing registry stay unchanged. A task must be the exact current reviewed approved revision, or an exact replay of an already-published revision with its publication proof intact. Draft, paused, overdue, altered and unsupported work is refused. This command creates no approval, commit, PR, deployment, email or scheduler.

The initial rendering adapter supports existing generic authority routes only. Separately owner-gated services and case-study routes are excluded. The canonical route and language must match; a supplement cannot duplicate an existing static section. Promoting the candidate to `lib/editorial/published.json` is a normal reviewed source change: existing CI and deployment gates still run. An existing supplement on the same target is replaced as a whole, not accumulated indefinitely. The public payload contains only the selected heading/paragraphs, target/language, an opaque reviewed revision, public-byte checksum and the actual review date used for content modification. Private source notes, reviewer identity, rationale and queue scheduling do not enter the website.

The server validates the complete public manifest before rendering. Malformed, unsupported, duplicate or checksum-inconsistent entries fail the build instead of disappearing silently. React renders the approved text as ordinary text, without raw HTML or arbitrary executable markup. The same manifest supplies real content dates to the sitemap, retaining any newer date for other changes to the page. It does not add routes, language clones, FAQs, authors, experience claims or structured-data types. An overdue private review blocks a new staging run; it does not silently remove an existing live page.

The public checksum detects changed bytes; it is not an owner signature and cannot authenticate reviewers. Repository/source-review access remains the publishing authority. The public renderer never reads the private queue or calls a content provider. The first migration replays the owner's already approved compliance text, replacing its old hand-written copy so it appears exactly once. Normal source, native-browser and actual production proof must confirm that the six paragraphs remain identical. Automatic discovery, drafting and an unattended scheduler are separate remaining work.

## Automatic verification after production deployment

The `Editorial production postflight` workflow listens for successful Production deployment statuses, plus an explicit diagnostic manual run. It reads public data only and has read-only repository permission. It checks that the deployed SHA is still main, checks out that exact source and runs `content:verify-live` against the fixed production origin. Superseded deployment events are explicitly skipped; preview and failed-deployment events do not start a check. The existing approved Ubicloud runner is reused. There is no recurring timer, new credential, private queue upload, provider call, deployment or automatic rollback.

The command verifies every public manifest section once, exact heading/paragraphs, canonical, language, indexability and the corresponding sitemap date. React transport data, comments and styles cannot stand in for rendered HTML. Three bounded attempts allow deployment/cache propagation; a failure is recorded rather than marked published. The public-only report is retained as an artifact. It does not measure rankings/leads, verify browser visibility or replace native tests. A checksum is still not reviewer authentication. Workflow trigger behavior follows [GitHub's deployment_status documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#deployment_status).

## Existing employer landing-page slots

Four existing English landing routes are explicitly wired: in-house counsel, legal leadership, law-firm recruitment and European cross-border recruitment. Their route entrypoints are server components; the existing interactive page shells remain client components and receive only a rendered editorial ReactNode inside main, before the enquiry section. The manifest and Node validation code do not enter their browser JavaScript. Empty slots render nothing; no new text, approvals, fees, dates or translations are created by wiring the adapter.

The target registry includes their observed existing headings to prevent accidental duplication. Other custom landing routes and unsupported language variants remain excluded. Every promoted manifest entry is additionally checked by native CI for one visible heading/section, exact paragraphs and its own canonical/language. Production postflight rejects duplicate matching headings elsewhere on the page too. Server/client interleaving follows [Next.js's documented ReactNode/children composition](https://nextjs.org/docs/app/getting-started/server-and-client-components#interleaving-server-and-client-components).

## Reviewed publication calendar

`content:stage` accepts optional `--publish-on YYYY-MM-DD` for a future UTC publication day. The task still needs the exact current reviewed approval. Its publication day must precede its next-review date. The resulting public candidate keeps the current supplement in place and puts the new reviewed bytes into a separate calendar. Rescheduling the same pending task replaces its pending slot; it does not duplicate it. An immediate replacement is refused while unresolved future work would later overwrite the same target.

The server chooses the latest version due on the current UTC day, on each evaluation. Unreleased text is not rendered into page HTML or sent through the client slot. The same selected version supplies sitemap content dates; a future plan cannot manufacture a future lastmod. The scheduled content date is the intended publication day, not a claim that the review happened on that day. Source promotion remains the ordinary reviewed change with all existing gates. No live publication proof is created merely by placing a future entry in the calendar.

Pages and the three sitemap endpoints revalidate after60seconds so an approved time transition does not require another deployment. Actual visibility can follow the first request and cache regeneration; it is not a guaranteed midnight transaction. A read-only daily production check at01:15UTC checks the current main against actual public text. It uses the same fixed-origin verifier and read-only permissions as the deployment postflight; no content generation, write token, CRM access or private queue is introduced. The first real cron invocation remains a separate future observation; deployment/manual events must not be relabelled as schedule events.

Use `pnpm content:calendar --registry lib/editorial/published.json --action pause --output /absolute/new-paused-candidate.json` to snapshot what is currently visible and hold the remaining schedule. Repeated pause preserves the original cutoff. Use action `resume` with a new output to release held work that still has a valid review; the latest due version gets the actual resume day, rather than a backdated missed date. Expired held work is refused until its review is renewed. Future work remains scheduled. Both commands create only a new mode0600 candidate and require normal reviewed promotion; they never overwrite the registry or private queue. Rollback uses the recorded previously verified source commit and its normal deployment checks.

Calendar hashes detect changed scheduled bytes/dates, not owner identity. Unsupported routes/languages, static-heading collisions, inconsistent IDs, conflicting slots, reversed content dates and unchanged-text re-dating are refused. The current compliance text remains identical and immediately visible; no real new text or owner review is invented by adding the calendar mechanism.

Native CI first tests the unmodified publication source. Only in the separate disposable fixture build, a GitHub-CI-only script substitutes two clearly synthetic scheduled records on existing routes. A browser then checks a due section on the real route, absence of future copy from raw HTML and DOM, and no future sitemap date. That temporary source is never committed, deployed or used by production postflight. The script refuses to run outside GitHub CI or in a Vercel environment. Widget tests retain their intercepted provider/contact responses and the public dummy key only in this same disposable build.

A renewed review of unchanged visible text keeps its previous content modification date. It does not create apparent freshness for SEO. Production verification also checks that unselected scheduled/superseded versions are absent from their editorial sections. The actual owner-reviewed leadership and partner-integration texts use the same ordinary source and runtime calendar path; private review identities and evidence notes remain outside Git.
